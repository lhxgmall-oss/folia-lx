## 起因：现在的浪费

| htdemucs | automix 在 CPU（MNN）上分固定的头尾各 30 秒四轨（`services/automix/stems.ts`，只在内存里）；智能动感在 GPU 上整首再分一遍，只留鼓轨、其余三轨丢掉（`services/analysis/drumStem.ts` → `drumHits.ts`）。两边分段起点不同，结果没法互用 |
| 显存 / 内存 | 两边各自常驻，没有统一预算。automix 的 CPU 分离峰值约 530 MB，两边同时跑约 1.1 GB |
| 切换画面 | PR #734 的临时做法：鼓轨分离切画面不停，后台跑完（见「暂停与续算」；2b 已替换） |
| 排队 | `beatThisGpu.ts` 的 `queue` 是一条 FIFO 链，不分轻重缓急，也不能暂停 |

## 目标架构：功能只提交任务，调度层决定一切

```
  automix ──┐  提交任务            ┌─ GPU 执行器（渲染进程 Worker，beatThisGpu.worker.ts）
            ├──────────> 调度层 ───┤    beat_this final0、htdemucs，默认
 智能动感 ──┘  去重·缓存·排队·     └─ CPU 执行器（MNN 子进程，electron/analysis）
               选执行器·暂停           beat_this final0、htdemucs，只作后备
```

- 功能只说要什么、多急：这首的拍点 / 鼓点 / 某段时间的四轨，automix 另带截止时间。不管模型，也不管在哪跑。
- automix 默认也在 GPU 上跑，和智能动感一样；CPU 只在 GPU 不行或赶不上时用（见「选执行器」）。automix 里关于模型和执行器的代码删掉，过渡逻辑不动，只换提交入口。
- 智能动感仍只走 GPU（智能动感三档的规则不变）。

### 任务

```ts
interface AnalysisTask {
  kind: 'beats' | 'drumHits' | 'stems';
  key: string;                  // 歌的分析 key + 数据种类（stems 再加时间范围），去重用
  deadline?: number;            // automix 才有：过渡开始的时刻（当前这首剩余时长减去过渡长度）
  urgency: 'transition' | 'onScreen' | 'background';
  stillWanted(): boolean;       // automix 现有的 stillWanted 沿用
  units(): AsyncIterator<Unit>; // 拆成小块：htdemucs 一段 3.9 秒，beat_this 一个 chunk
}
```

### 排队：每跑完一块重新挑下一块

`beatThisGpu.ts` 的 `queue` 换成挑选循环。每块跑完后按下面顺序挑：

1. 有截止时间的任务，余量（截止时间 − 预计完成时间）最小的先跑；
2. 屏幕上正在显示的效果要的；
3. 后台预取；
4. 同级里先来先跑。

暂停的任务（见「暂停与续算」）不参与挑选。`stillWanted()` 为 false 的任务在块边界丢弃。

### 「忙不忙」：按预计完成时间判断

WebGPU 没有接口能读 GPU 占用率，所以不测占用率，测**每块要多久**：

- 每跑完一块记下耗时，按（任务类型，执行器）分别做滑动平均。
- 预计完成时间 = 现在 + 排在它前面的块数 × 平均耗时 + 它自己剩下的块数 × 平均耗时 + 模型加载时间（模型没加载时）。
- 「忙」的定义：预计完成时间加上安全余量，晚于截止时间。

### 选执行器

```ts
function chooseExecutor(task) {
  if (!gpuAvailable) return 'cpu';                   // 没有 WebGPU、GPU 掉线
  if (!task.deadline) return 'gpu';                  // 智能动感只走 GPU
  if (etaOn('gpu', task) + MARGIN < task.deadline) return 'gpu';
  if (etaOn('cpu', task) + MARGIN < task.deadline) return 'cpu';
  return 'gpu';  // 都赶不上：照常跑，过渡时没分轨就退回普通交叉淡化（现有行为）
}
```

- 任务开始时选一次；运行中只在出错时换（GPU 掉线就把剩下的块交给 CPU），不来回切。
- automix 通常有几分钟提前量，一个 30 秒窗口在 GPU 上约 8 段、不到 1 秒，所以实际上几乎总是 GPU；截止判断主要是兜底，常走 CPU 的是没有 GPU 的机器。

### CPU 线程数也由调度层定

现在是写死的（`electron/analysis/worker.cjs`）：beat_this 用逻辑核数的 1/4（`THREADS`），htdemucs 固定 4（`HTDEMUCS_THREADS`），在加载模型时定下（每个模型一个 MNN executor，`native/folia-mnn/folia_mnn.h`）。改成调度层按任务选两档：

- **安静档**（默认）：逻辑核数的 1/4，至少 1，htdemucs 最多 4。没有截止压力的任务都用这档。beat_this 现在就是这个数；htdemucs 现在固定 4，在小机器上太多（4 核机器等于占满，8 核机器占一半），改成同一条规则（用户 2026-10-17 提出）：24 核仍是 4，10 核（M4）2，8 核 2，4 核 1。安静档变慢由赶时间档兜底，所以和赶时间档同一步上线，不单独先改。
- **赶时间档**：安静档下预计赶不上截止时间时用，约逻辑核数的一半。不再往上加：`worker.cjs` 里的实测是线程多了反而慢（24 核机器上 24 线程 3547 ms，12 线程 1438 ms，6 线程 1602 ms）。

规则：

- 预计完成时间按（任务类型，执行器，线程档）分别统计，选执行器时 CPU 两档都算：先看安静档赶不赶得上，不行再看赶时间档，再不行才「照常跑、过渡退回交叉淡化」。
- 只在块之间换档；赶上了就退回安静档。
- 档位上限按机器核数算，不按固定数字，比例和现在一样「不随机器大小变」。
- 待验证（阶段 2）：MNN 能否在不重建模型的情况下改 executor 的线程数。能就块之间直接改；不能就只在任务开始时选档，换档要重建模型（htdemucs 在 CPU 上的加载耗时见 `worker.cjs` 的日志），并把这个耗时算进预计完成时间。

### 画面掉帧时让路

推理块和可视化渲染抢同一块 GPU。也按测量处理：

- 渲染循环报告帧间隔；跑推理块期间如果两帧间隔超过目标的 1.5 倍，就在块之间多停一帧再派下一块，连续掉帧时逐步加长间隔，恢复后缩回。
- 有截止时间且余量不够的任务不让路（宁可掉一两帧，也不让过渡没有分轨）。
- 先在阶段 2 里加上帧间隔的日志实测，再按实测定阈值和间隔；这一步要做，不是可选项。

实现（2c，`scheduler.ts`）：一块跑完时看这块期间有没有掉帧（帧间隔超过最近 120 帧里最短间隔的 1.5 倍）。掉了，下一块派出前先等 1 帧；接着还掉就翻倍，最多 8 帧；一块没掉就减半，直到 0。下一块有截止时间、余量不到 5 秒的不等。页面隐藏时没有帧，等待按每帧 100 ms 超时结束。阈值和上限是初值，等实测日志（`[Scheduler] ... frames:`）再调。

审查后补的（掉帧不一定是推理造成的）：
- 等待的那几帧也看帧间隔：没有推理在跑也掉帧，说明是画面自己掉（画面本身重、120 Hz 屏上 60 fps 的画面、偶发卡顿），等也没用，直接回到连续派发。
- 等待靠超时结束（一帧都没来）或推理期间一帧没画：窗口最小化或被挡住（主窗口 `backgroundThrottling: false`，页面一直算「可见」），没有画面可让，也回到连续派发。
- 等待的帧数算进预计完成时间；等待的那块被丢掉时，等待不顺延给下一个新任务。
- 日志：让路帧数每次变化都打印原因；每块的日志写出其中多少是为画面等的。

## 暂停与续算：只留结果，回来续算

用户的要求（2026-10-17）：一个推理被切走时，只保留它已经算出的结果，不在后台接着跑、也不占资源；切回来从断点接着算，不从头来。

现状（PR #734 里的临时做法）：鼓轨分离切画面时不停，在后台跑完并存盘，只有换歌、关掉智能动感或开静态模式才停（`hooks/useBeatFxTrack.ts`）。代价是切到别的画面后，这首的分离还在和新画面的推理分 GPU 队列，解码出的整首音频（4 分钟约 80 MB）也一直留到分完。

目标做法：

1. **任务可中断**：分段任务每段之间检查还要不要，不要了就停在段边界。
2. **只留结果**：停下时保存已经算完的部分和续算需要的最小状态，丢掉别的：
   - 鼓点：到 `until` 为止的鼓点列表（几 KB），加上下一段的起点、和下一段重叠的那一截鼓轨（拼接要用，约 1 秒）、`drumHitStream` 已出的频谱帧位置。
   - 解码出的整首音频、GPU 上的中间结果都不留。
3. **回来续算**：再要这首时，先用保存的鼓点立刻出效果，再重新解码（不到 1 秒），从断点那一段接着排队，整首完成后存盘、丢掉续算状态。
4. **断点只放内存**（已定）：按歌的 key 放在内存 LRU 里，只留最近几首，不写盘。写盘会把没算完的东西也存下来；磁盘上只存算完的结果（拍点、鼓点）。被挤掉或重启后，下次从头分。
5. **谁优先**：被切走的任务暂停，不算「没人要」，换歌才算。

实现（2b）：
- `drumStem.ts`：分离的进度（累加和、权重、下一段、已除完的位置）是 `DrumStemProgress`，可以从中途接着跑。
- `drumHits.ts`：停在段边界时，先把能量和频带补到已除完的位置，再存 `DrumResume`（最近 4 首，只在内存）：已出的鼓点、下一段、频带和 `done`、累计的鼓轨能量、以及鼓轨从「频带 / 能量下次要读的位置」到「已分段落到达的最后一个采样」那一截和它的权重（约 1 秒）；频带和能量只存已经算到的部分。一首约 0.4 MB 加上每秒已分离音频约 0.3 KB，整首音频和整条鼓轨都放掉。断点在这首分完或下次停下另存时才丢，分离中途抛错不丢。
- 回来时先放回已出的鼓点，再解码，长度和停下时不同就从头分；分完存盘、丢掉断点。鼓轨能量改成边分边累加，和原来整条一次算的加法顺序一样，结果逐位相同。
- `useBeatFxTrack.ts`：鼓点效果退出（切画面、换歌、关开关）时 `setWantedDrumTrack(null)`，分离在下一段之前停下。
- 单测：中途停下、只带那一截续算的鼓轨，与一口气分完逐位相同；频带流从保存的频带接着读，与一口气读完逐位相同；端到端（`drumHitsResume.test.ts`）：真的分段、频带流和断点，`setWantedDrumTrack(null)` 中途停下再 `loadTrackDrumHits` 续上，存盘的鼓点和能量与一口气分完逐位相同，只跑剩下的段，回来时先放回已出的鼓点；读不到字节时放回的鼓点会再撤掉。

## 结果复用：同一首歌只用一套分段

htdemucs 是一段一段算的（约 3.9 秒一段，相邻重叠 1/4，再拼起来，`drumStemSegments`）。现在智能动感从整首开头切，automix 从「末尾往前 30 秒」切，两边的段错开，结果不能互用。

1. **固定分段**：每首歌都从第 0 个采样点开始切，第 k 段从 k × 段长 × 3/4 开始，谁算都是同一段。共享的单位是「歌 + 段号」的原始四轨（拼接前的模型输出），谁算出来谁放进去，谁要谁取。
2. **automix 按时间范围要**：窗口不再固定 30 秒。automix 提交「这首某一段时间的四轨」，调度层换算成覆盖它的段号（两头各多一段供拼接），有的直接拿、缺的去算，拼好交回。歌一开始可以先要默认范围（如最后 30 秒）；规划器定下的切出点不在里面时，只补缺的段（规划器的重叠最长 `AUTOMIX_MAX_OVERLAP_SEC` 25 秒）。
3. **两个方向都复用**：
   - 智能动感分整首时，模型每段本来就出四轨，不再把另外三轨丢掉，按下面的规则留下，automix 要的范围多半现成。
   - automix 先分了下一首的开头几段：播到那首时，时计的鼓点直接从这几段的鼓轨开始，整首分离跳过这几段。
4. **逐位一致**：同一个模型、同一套分段、都在 GPU 上，拼出的结果和一口气分完整首逐位一致（单测验证）。
5. **留哪些段（只在内存）**：
   - 整首全留太大（四轨 16 位，4 分钟约 170 MB）。
   - 固定留头尾各 30 多秒（约 11 段，每段约 2.8 MB，一首头尾约 60 MB），其余段提取鼓轨后就扔。
   - 只给最近几首留，按最近使用淘汰，总量封顶（同 automix 现在 `MAX_WINDOWS` 的思路）。
   - 存原始段因为有重叠，30 秒约 30 MB，比现在拼好的 21 MB 多约 40%。先用简单做法，量过内存再决定要不要改成「内部存拼好的、两端各留一段原始输出」（回到约 21 MB）。
6. **前提**：同一首歌两边解出的采样必须逐位相同（阶段 1），两边都在 GPU 上（一边 CPU 只能做到 0.01 dB 以内，逐位一致不成立）。没有 GPU 的机器整套照旧走 CPU。

## 阶段 3 进度

- ✅ GPU htdemucs 一次出四轨，改用 f32（用户 2026-10-17 定：f32 过 0.01 dB 红线，f16 的 bass 不过；每段慢约 9%）。
- ✅ `analysis/stemRange.ts`：固定分段网格上按时间范围分四轨，与整首在这些采样上逐位相同；段缓存（96 MB 上限，LRU）：automix 说要的范围里的段，谁分出来都整段留给它；automix 分出来的段留鼓轨给之后的智能动感；automix 拿到后段缩成只留鼓轨。鼓轨分离改走这里。
- ✅ automix 分轨默认走 GPU（调度层、后台优先级），GPU 不行时退回 CPU；有截止时间且 GPU 赶不上、CPU 赶得上时走 CPU；CPU 线程按调度层的档（安静：核数 1/4、htdemucs 最多 4；赶时间：约一半）。MNN 线程数在建模型时定死，换档要重建（日志记加载耗时）。
- ✅ automix 传截止时间：过渡最晚开始准备的时刻（歌尾前最长重叠 + 预备时间），首尾两个窗口都用它。按调度层的排法，有截止时间的块排在屏幕上的鼓轨分离之前（一个 30 秒窗口约 10 段，GPU 上约 1.3 秒）。
- 待做：automix 实测；智能动感和 automix 同一首歌共用分段的实测。

## 阶段 4：模型常驻

实测（M4，测试壳）：GPU 上 htdemucs（f32、四轨）占 350 MB，beat_this 占 106 MB。苹果芯片是统一内存，这就是整机内存。

- GPU（`beatThisGpu.ts`）：每个模型闲置后各自释放，htdemucs 30 秒（一首歌的分段集中在开头那十几秒）、beat_this 1 分钟，不再等整个 worker 闲置 2 分钟一起走；设备和 worker 照旧 2 分钟。预算 512 MB：加载会超出时先释放最久没用的另一个模型。正在跑的模型不会被释放。
- CPU（`electron/analysis/worker.cjs`）：有 GPU 的机器上，CPU 只是回退，加载的 htdemucs（约 400 MB）闲置 1 分钟就释放；没有 GPU 的机器照旧在 automix 开着时常驻。
- 每个模型加载时日志写出它在 GPU 上占多少。
